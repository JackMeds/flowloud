# Flowloud 产品体验审计

日期：2026-08-25  
版本：0.10.0-alpha.1  
运行源：`extension/`  
审计模式：真实 Chromium + 真实网站 + 扩展运行态 + 可控 TTS 状态探针

## 结论

**综合评分：7.6 / 10（76 / 100）**

Flowloud 已经不是“功能拼出来但体验不闭合”的原型。核心朗读链路、Popup、设置中心和文档工作台已经形成统一的蓝白视觉系统，真实站点上的播放、暂停、逐词反馈和状态保持也具备可靠基础。当前最影响产品质感的不是基础功能，而是两个会被用户立即感知的网页内问题：**悬浮入口隐藏得过深**，以及**当前句标记与网站原有内容发生碰撞并暴露内部 Provider ID**。

如果先修这两个问题，再把语音来源设置改成渐进式配置、把工作台前置条件变成明确的可操作提示，整体体验可以从 7.6 提升到约 8.5。

## 审计范围与验证结果

- 覆盖流程：首次使用 → 真实文章自动注入 → 悬浮入口 → 展开播放器 → 播放/暂停/逐词反馈 → Popup 快捷设置 → 完整设置 → 文档与翻译工作台。
- 真实站点：Wikipedia 中文文章，以及现有真实论坛矩阵。
- 浏览器回归：5 项通过，2 项按预期跳过；Linux.do 被 Cloudflare 挑战页阻挡，未误判为扩展失败。
- 本次截图运行没有发现扩展归属的控制台错误。
- TTS 探针确认页面被提取为 68 段，播放进入 `playing`，逐词索引开始推进；没有依赖人工听音。

## 流程步骤与健康度

### 1. 首次使用：良好

![首次使用](assets/01-onboarding.png)

优点：主标题有辨识度；“系统语音、本机处理、不自动下载/上传”直接建立信任；主次按钮清楚。键盘第一次 Tab 会进入主按钮，并显示明显焦点环。

![首次使用键盘焦点](assets/02-onboarding-keyboard-focus.png)

问题：页面告诉用户“打开文章并点击扩展”，但没有展示或解释网页右侧会自动出现的悬浮入口；“浏览器模型、本地 Qwen、在线 TTS”在首次启动阶段略偏技术化。

### 2. 真实网页中的收起入口：需改进

![真实网站收起入口](assets/03-reader-collapsed-real-site.png)

右下角入口被设计为 Edge Peek，仅留下约 10px 可见区域。对已经知道入口位置的用户尚可，但第一次使用几乎没有足够的形状、图标或文字提示去解释“这里可以展开播放器”。核心入口的可发现性因此低于整个产品其他部分。

### 3. 展开播放器：良好，但偏小

![展开播放器](assets/04-reader-expanded-ready.png)

![播放器细节](assets/04a-reader-player-detail.png)

优点：252px 卡片能同时表达角色、段落、当前句、进度、上一句/播放/下一句/定位/收起，层级非常紧凑；主操作蓝色明确，状态变化不依赖文字说明。

问题：正文只有约 11px，元信息约 10px，五个控制按钮为 32×32px。它们满足最低可点击要求，但在高 DPI、触控板误触或视觉能力较弱的场景下不够从容。建议正文提升到 12–13px、按钮提升到 36–40px，卡片宽度可增加到 272px。

### 4. 播放、逐词反馈与暂停：功能健康，页面融合存在风险

![播放与逐词反馈](assets/05-reader-playing-highlight.png)

当前句以浅蓝背景和左侧细线标识，当前词进一步使用蓝色强调；播放按钮切换为暂停图标，暂停后又恢复为播放图标，状态可辨识。

但行内控制标记出现在正文左侧时，会横跨 Wikipedia 的目录区域，并显示类似 `browser-system:Flowloud...` 的内部 Provider 标识。它与网站已有链接竞争空间，既像调试信息，也降低了品牌完整度。

![行内标记碰撞细节](assets/05a-reader-marker-detail.png)

![暂停状态](assets/06-reader-paused.png)

### 5. Popup：良好

![Popup 声音设置](assets/07-popup-sound.png)

优点：顶部先回答“现在读到哪里”，中间给 transport 控制，下面才是点读、悬浮播放器和分类设置，优先级正确。声音、阅读、配音、更多四类也比长表单更适合瞬时小窗。

![Popup 阅读设置](assets/08-popup-reading.png)

![Popup 更多设置](assets/09-popup-more.png)

问题：播放摘要、三个快捷动作、四个 Tab 和内容卡同时存在，600px 高度内信息密度已经接近上限。后续不要再往首屏增加新功能；低频能力必须继续放入“更多”或完整设置。

### 6. 完整设置：良好，语音来源页需要收敛

![完整设置概览](assets/10-settings-overview.png)

侧栏按任务而非技术模块命名，卡片、保存状态与开关关系清楚；900px 宽窗口下也能保持稳定布局。

![语音来源](assets/11-settings-reading-engines.png)

![窄窗口语音来源](assets/13-settings-reading-engines-narrow.png)

主要问题：语音来源页把浏览器模型、本地服务、在线 TTS、豆包 TTS 的所有配置连续堆在一个约 2659px 高的页面中。用户只选择一种来源，却必须理解所有来源的字段。建议改为：顶部来源卡 → 选中一个来源 → 只展开该来源的状态、说明和配置。状态语言也应固定为“可用 / 未配置 / 需下载 / 待检测 / 连接失败”，避免绿色卡片同时写“使用时检查权限”这种含糊状态。

### 7. 文档与翻译工作台：可用，但前置条件处理不足

![文档与翻译工作台](assets/12-document-workbench.png)

三步式结构清楚：左侧选输入与流程，右侧校对和朗读；空状态没有伪造结果，隐私文案也放在操作附近。960px 窗口下仍可使用。

![窄窗口文档工作台](assets/14-document-workbench-narrow.png)

问题：OCR 与翻译服务均为“未选择”时，“开始处理”仍是强蓝色可操作按钮，用户只能在点击后从底部状态文字得知前置条件。建议在按钮上方直接列出缺少项，并将按钮替换为“配置 OCR/翻译服务”；条件满足后再显示“开始处理”。

## 动效审计

当前动效总体是产品优势，不需要重做：

- 播放状态波形：900ms 循环，用于持续表示正在播放。
- 悬浮快捷操作：透明度 120ms、位移 160ms。
- 字幕进入：180ms。
- 进度更新：180ms。
- 正常的界面反馈集中在 120–220ms，节奏一致，没有拖沓的装饰动画。
- `prefers-reduced-motion` 会关闭播放器、快捷操作、加载器和播放波形的动画；扩展页面的全局设计系统也会禁用动画和过渡。

建议保留现有节奏，但调整动效的承载位置：

1. 收起入口至少保持 28–32px 可见；首次三次访问可做两轮轻微呼吸提示，然后停止。
2. 播放波形、暂停图标和错误图标继续同时使用形状与颜色，不要只依赖动画。
3. 行内标记从正文边缘短距离出现，不要横穿侧栏；空间不足时退化为正文上方的窄条。
4. 暂停后冻结当前词与进度，当前实现已经基本符合这一点。

## 可访问性

本次确认的优点：

- Onboarding 的首个键盘焦点正确且可见。
- Popup 主要控制具有可访问名称。
- 播放状态使用 `aria-live` / `role=status` 进行更新。
- 阅读器提供 reduced-motion 和 forced-colors 规则。
- 主文本与白底、蓝色主按钮与白色图标没有发现明显的截图级对比度问题。

仍需验证或改进：

- 收起入口实际可见部分远小于其 44px DOM 命中区域；用户看不到的命中面积不能替代可见目标。
- 展开播放器的 32px 控件与 10–11px 辅助文字偏小。
- 行内标记与网站目录重叠，会影响视线和点击目标。
- 本轮没有运行读屏软件、200%/400% 缩放和完整键盘遍历，因此不能声称达到完整 WCAG 合规。

## 优先级建议

### P1：先修，直接影响核心体验

1. **提高悬浮入口可见度**：默认至少露出 28–32px；只有用户主动拖到边缘后才进入 Peek；首次使用显示一次解释性提示。
2. **重做行内标记的空间策略**：移除内部 Provider ID，显示人类可读的“正文 · 系统语音 · 1/68”；检测可用边距，空间不足就放到正文上方或只保留细线。
3. **语音来源渐进式配置**：未选中的 Provider 不展开表单；统一连接状态语义。
4. **工作台前置条件门控**：缺少服务时显示配置 CTA，不允许强主按钮把用户带进可预见错误。

### P2：随后优化，提升质感与可访问性

5. 播放器正文提升至 12–13px，按钮提升至 36–40px。
6. Onboarding 增加一张“网页右侧入口 → 展开 → 播放”的小示意，并弱化模型术语。
7. Popup 保持当前功能边界，不再向首屏追加卡片；可把“回到正文”并入播放器的定位按钮说明。
8. 为 900px 以下的工作台增加单列断点，避免标题和结果操作在更窄窗口继续挤压。

## 建议的自动验收标准

- 在 1440×900、900×760 两个视口捕获收起、展开、播放、暂停四种状态。
- 收起入口至少有 28px 可见，鼠标、键盘焦点和高对比模式均可识别。
- 行内标记不得与站点已有可点击元素发生几何重叠，不得出现 Provider 内部 ID。
- 语音来源页只展示当前来源的详细表单，状态必须属于固定状态集合。
- 工作台缺少必需服务时，主流程不得进入执行状态。
- 定向场景通过后，继续运行真实站点矩阵和完整浏览器套件。

## 证据限制

- 音频连续性使用确定性 TTS 事件验证，没有把扬声器输出当成唯一证据。
- Chromium 的工具栏 Popup 需要真实浏览器 UI 用户手势；本次 Popup 图片使用正式 React 页面，并注入同一轮 Wikipedia 运行态快照进行视觉审计。Popup 的布局、文字和控件是真实发布代码，但“点击工具栏图标打开”这一瞬间未截图。
- Linux.do 的 Cloudflare 挑战属于外部阻塞。
- 截图只能证明可见状态；读屏、缩放、认知负荷和长期使用体验仍需要专项验证。
