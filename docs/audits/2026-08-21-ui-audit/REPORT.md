# 浏览器 TTS 前端深度审计与优化计划

日期：2026-08-21  
审计对象：浏览器扩展 Popup、设置中心、悬浮播放器  
代码基线：`codex/sync-latest-project` / `fa296f5`

## 执行结论

这次体验差并不是因为“HTML 做不出好设计”。HTML 只负责结构；最终质量取决于信息架构、CSS 状态设计、渲染策略和验收方式。当前项目在这四层同时出现了问题：

1. Popup 最初是原型式实现：每 900ms 轮询一次，一旦状态签名变化，就重建整个根节点。
2. “纸张重置”没有清理旧体系，而是在旧 CSS 上继续叠加主题覆盖层；组件状态发生选择器冲突。
3. 设计目标主要来自一张 AI 生成的静态效果图，验收也偏向尺寸、截图和字符串契约，没有验证真实交互过程。
4. 全局设置、本页设置和本页配音混在一个最大高度 600px 的临时 Popup 中，信息范围和入口层级不清楚。

因此，用户看到的是一组互相关联、并非偶然的症状：界面简陋、滚动位置复位、折叠项自动关闭、深色按钮悬浮后变白、设置入口拥挤且语义矛盾。继续追加 CSS 补丁只会扩大维护成本；应先修状态生命周期，再重整信息架构，最后统一视觉系统。

| 优先级 | 发现 | 用户影响 | 根因 |
| --- | --- | --- | --- |

| P1 | 370 项测试全部通过，但上述缺陷仍存在 | 测试产生虚假安全感 | 测试偏字符串契约、尺寸和静态截图；没有验证滚动、展开、hover 和周期刷新 |

## 复现证据

### 1. Popup 初始状态：可用，但主次层级弱且内容过载

![Popup 总览](01-popup-flow-overview.png)

优点：播放控制尺寸足够大，基础标签和焦点样式已有考虑。  
问题：播放主任务与设置任务挤在一条长页面中，默认流程已经接近平台高度上限。

Chrome 扩展 action popup 的最大尺寸为 800×600，且焦点转移后会自动关闭；这类临时界面不适合承载长表单和多作者编辑。[Chrome action popup 文档](https://developer.chrome.com/docs/extensions/reference/api/action)

### 2. 展开“本页选项”并向下滚动：状态暂时正常

![刷新前的滚动与展开状态](03-popup-scrolled-open-before-refresh.png)

健康度：有缺陷风险。此时用户正在操作下半部分，但页面状态只存在于即将被替换的 DOM 中。

### 3. 模拟下一次播放快照：滚动和展开状态丢失

![状态刷新后回到顶部](04-popup-reset-after-refresh.png)

健康度：阻断性缺陷。状态变化触发整棵 Popup DOM 替换，新的滚动容器从 `scrollTop = 0` 开始，新的 `details` 也默认为关闭。`replaceChildren()` 会用新节点替换现有子节点，这与代码行为吻合。[MDN：Element.replaceChildren()](https://developer.mozilla.org/en-US/docs/Web/API/Element/replaceChildren)

### 4. 主按钮 hover：视觉和可访问性同时失败

![主按钮 hover 对比度失败](05-primary-button-hover-contrast-failure.png)

健康度：阻断性缺陷。背景从深紫色变成 `rgb(246, 243, 237)`，文字仍为白色；计算对比度约 1.11:1。

### 5. 设置中心：功能可用，设计系统割裂

![设置中心阅读页面](07-settings-reader-1280.png)

健康度：勉强可用。页面外壳是扁平纸张风格，内部仍有旧紫色卡片、旧圆角和旧阴影；信息层级主要靠零散留白维持，宽屏下显得空且弱。

### 6. 悬浮播放器：基本可用，但可发现性不足

![悬浮播放器播放状态](09-floating-player-playing-1280.png)

健康度：基本可用。核心播放入口存在，但拖拽区域、收起方式和次级控件缺少显式提示。其问题低于 Popup 的状态复位和 hover 错误。

## 代码与历史诊断

### 问题不是一次“重置”凭空造成的，而是两个阶段叠加

- `1045d4d` 的 Popup 原型已经包含轮询和整根重建，埋下滚动复位的结构性缺陷。
- `fa296f5` 的纸张重置加载了 `design-system.css`、`popup-paper.css`、`settings-paper.css`，但保留旧 CSS；同时新增折叠设置后，内容达到 600px，潜在缺陷变成稳定可见的问题。
- 同一提交的设计 QA 主要验证 390×600、44px 控件、截图和重排，没有覆盖“滚动中发生播放状态更新”这一真实场景。

### 直接证据链

1. `popup.js` 每 900ms 获取一次快照，渲染签名包含播放状态、索引、总数和当前内容。
2. 任何这些字段变化都会进入 `mountPopup()`。
3. `mountPopup()` 调用 `root.replaceChildren()`，销毁并重建 `.qr-popup` 滚动容器。
4. 实现只捕获并恢复焦点，没有保存 `scrollTop`、`details.open` 或局部编辑状态。
5. 测试只确认存在焦点恢复和渲染签名，没有做状态连续性断言。

### 为什么会显得“明明很简单，却到处不合理”

这是典型的局部任务通过、整体体验失败：

- 静态图驱动的是“长什么样”，没有定义“状态变化时怎么保持用户上下文”。
- CSS 覆盖驱动的是“尽快换皮”，没有建立主按钮、次按钮、hover、focus、active、disabled 的完整状态矩阵。
- 字符串契约测试驱动的是“代码里有没有某个东西”，没有证明用户能否完成任务。
- 功能不断塞入 Popup，却没有重新决定 Popup 应该负责什么。

## 推荐的信息架构

### Popup 只保留即时任务

1. 当前页面标题、播放状态与进度。
2. 上一句 / 播放暂停 / 下一句。
3. 一个紧凑的速度与声音入口。
4. 一个清楚的“本页”入口和一个“全部设置”入口。

### 设置作用域必须显式分开

- `显示悬浮播放器`、`点击朗读` 当前是全局持久化：应重命名为“网页交互（全局）”，可以用两个紧凑、常显的开关，不应伪装成“本页选项”。
- 预设策略如果也是全局：放入“声音与配音策略”，不要混入本页分组。
- 真正的页面级配置：只保留一个“本页配音”入口，显示当前规则摘要。
- 多作者映射属于复杂表单：建议打开独立扩展页或稳定的编辑视图，不放在会自动关闭且高度受限的 Popup 长流程中。

- 建立唯一的颜色、字号、间距、圆角、边框和状态 token。

验收：每个组件只有一处状态定义；不再依赖加载顺序修复颜色；全局搜索不存在遗留紫色渐变和无主覆盖规则。

### 阶段 4：设置中心与悬浮播放器打磨（已完成本轮范围）

验收：同一语义控件在三处界面拥有一致外观与反馈；键盘操作顺序自然。

### 阶段 5：建立真实 QA 闸门（已完成自动化范围）

## 2026-08-22 回归补丁：点击索引、暂停确认与悬浮球 v2

针对最新反馈又完成一次以行为为中心的回归修复，覆盖生产 reader、浏览器 harness 和发布包：

- 点击定位改为优先使用句子 Range 的真实屏幕几何位置，只有 Range 暂时没有可用矩形时才回退到浏览器 caret。这样即使 Chromium 在标点、零宽 inline 节点或论坛行边界把 caret 报到下一句，点击句子仍按实际命中句播放。
- 同一论坛楼层的多句、多切片不再依赖严格的单调游标；当 API 队列顺序、虚拟化 DOM 顺序或懒加载状态不一致时，会从正文起点寻找尚未占用的匹配范围，避免前一个未渲染切片把后续句子整体推偏。
- 暂停/继续控制将 `count=0`、响应丢失和 offscreen 交接窗口视为可重试状态，保留用户意图并按同一 playback identity 重试，不再把瞬时竞态直接提示为“流式播放无法暂停”。真实不支持时也改为等待确认文案，而不是把错误归因成能力限制。
- 网页悬浮球收敛为 36px 圆形 launcher，默认折叠；拖动后继续左右吸附，贴边露出约半个可点击球面；点击中心按钮负责播放/暂停，点击球面上下文区域展开紧凑 transport card，展开后才显示前后句、暂停和状态详情，语义与其它网页悬浮球一致。
